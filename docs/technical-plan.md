# 校赛电子证书系统技术方案

更新日期：2026 年 11 月 8 日。

系统采用 Vue 管理模板、Django API、PostgreSQL 和独立生成进程，通过 Docker Compose 部署。最初计划使用 Ubuntu 22 系列，当前验收主机实际为 Ubuntu 24.04；已实现与验证的版本、运行参数和处理速度以部署文档及验收证据为准。

业务范围以 [需求说明](requirements.md) 为准，尤其保留创建竞赛无需会签、获奖名单整批会签、部门管理员确认本部门公章、管理员可审批本人提交的批次、超管应急以及首期只按编号查验等规则。

## 技术选型

| 层次 | 方案 | 目的 |
| --- | --- | --- |
| 管理前端 | vue-pure-admin，Vue 3、TypeScript、Element Plus | 复用布局、菜单、用户部门管理、表单、表格、弹窗和预览示例 |
| 起始模板 | 官方 pure-admin-thin，按需引入完整版页面 | 减少与业务无关的演示代码 |
| 后端 | Python、Django 5.2 LTS、Django REST Framework | 复用账号、会话、权限基础、ORM 和数据库迁移 |
| 数据库 | PostgreSQL | 使用事务、唯一约束和行锁保证会签、编号与任务状态一致 |
| Excel | openpyxl，优先仅接收统一 XLSX 模板 | 导入获奖数据并生成带填写说明的模板 |
| PDF 签名 | pyHanko，配合 cryptography 管理证书和密钥 | 实现自签证书和多部门 PDF 签名 |
| 排版渲染 | 受约束 SVG 画布、共享排版 API 与 ReportLab PDF 渲染 | 统一字体、坐标、换行和正式输出；先验证再锁定画布依赖 |
| 后台任务 | PostgreSQL 持久化任务表和独立 worker | 实现排队、进度、租约、重试和中断恢复 |
| 文件存储 | 校内服务器持久化目录或 Docker 卷 | 存放背景、公章、模板快照和签发文件 |
| Web 入口 | Nginx | 提供前端静态文件、API 反向代理和受控文件下载 |
| 部署 | Docker Engine、Docker Compose | 管理服务、持久化卷、环境配置和版本交付 |

Django 已提供用户、分组、权限和会话等基础能力，适合作为本项目后台基础；部门、竞赛和批次的数据权限仍需专门实现。[Django 认证说明](https://docs.djangoproject.com/en/5.2/topics/auth/)

Django 5.2 属于长期支持版本。选取仍受支持的 Python 版本及对应补丁版，在容器中锁定依赖，不依赖 Ubuntu 宿主机的默认 Python。[Django 5.2 说明](https://docs.djangoproject.com/en/5.2/releases/5.2/)

上述选型根据本系统的复用条件和 PDF 签名需求作出。不会把 Django 的维护后台作为业务人员的另一套界面，三类用户统一使用 Pure Admin 页面。

## 前端复用方式

以官方精简版为基础，从完整版按需复用用户、角色、部门、日志、表格、上传、PDF 预览等页面和组件，沿用原有视觉样式。证书编辑器集成免费画布能力，工具栏、属性面板、列表和弹窗继续使用模板组件。

Pure Admin 官方推荐实际项目采用精简版；其完整版中包含系统管理和文件相关示例，可作为业务改造起点。[Pure Admin 官方说明](https://github.com/pure-admin/vue-pure-admin)

首期需要的业务页面包括工作台、账号与部门、竞赛与协作人、名单导入、批次预览、会签待办、模板库与编辑器、公章管理、生成任务、证书档案、作废申请、站内消息、编号查验设置和日志。

编号查验入口使用同一组件体系的简洁查询页。首期页面只提供已实现能力，后期功能保留在开发清单中。

## Docker 服务划分

| 服务 | 职责 | 持久化和网络 |
| --- | --- | --- |
| web | Nginx，提供前端及 API 入口 | 校园网入口；挂载访问证书和前端构建产物 |
| api | Django 与 DRF，处理账号、业务、审批及下载鉴权 | 内部网络连接数据库，使用受控文件目录 |
| worker | 排版、PDF 签名、图片与压缩包生成、定期维护任务 | 与 api 复用应用镜像，按最小需要挂载文件及签名密钥 |
| db | PostgreSQL，保存业务、会话、审计和任务 | 专用持久化卷，不向校园网直接发布数据库端口 |

备份由定期维护任务写入宿主机指定的本机备份目录。首期不强制增加外部对象存储或独立消息服务，后续任务规模增加时可以替换执行层。

Compose 管理多服务、网络和持久化卷；镜像标签或摘要需锁定，密钥通过受保护文件或配置注入，不写入仓库和镜像层。[Docker Compose 说明](https://docs.docker.com/compose/intro/compose-application-model/)

正式交付应包含镜像构建或离线导入方法、配置示例、数据库迁移、超管初始化、健康检查、启动升级、回滚和恢复说明。宿主机 Ubuntu 具体小版本需在部署前核实；Docker 官方当前支持 Ubuntu 22.04。[Docker Ubuntu 安装说明](https://docs.docker.com/engine/install/ubuntu/)

## 数据模型

| 实体 | 核心关系或约束 |
| --- | --- |
| 用户与部门授权 | 负责人使用独立全局角色组；管理员可关联多个部门；超管继承管理员权限 |
| 竞赛与协作人 | 一个竞赛关联多位负责人，保存实际创建人及授权变更 |
| 模板与模板版本 | 模板记录发布部门，版本内容固定，复制另存建立新模板 |
| 印章与印章版本 | 所属部门固定，支持多枚启用，历史版本不可覆盖 |
| 部门签名证书 | 记录公钥证书、密钥引用、有效期和启停情况 |
| 获奖批次与版本 | 冻结名单、模板、用印、输出和审批部门；新修改产生新版本 |
| 团队获奖记录 | 隶属批次版本，保留导入行和原始字段 |
| 部门审批决定 | 绑定批次版本及部门，记录实际审批人 |
| 提交与编辑人员 | 用于审计追溯，不再阻止具备本部门权限的管理员或超管审批 |
| 签发任务 | 保存输入版本、任务状态、租约、重试、进度和错误 |
| 证书与文件清单 | 全校唯一编号；关联团队记录、签发版本和每种文件摘要 |
| 作废申请与决定 | 保存目标证书及原盖章部门，状态独立于当前证书有效状态 |
| 业务审计与站内消息 | 保存操作人、范围、原因、前后值、时间和相关记录 |
| 系统设置 | 公开字段、姓名脱敏、限流、任务并发和清理期限等 |

编号有全局唯一约束；同一批次版本与获奖行只能形成一条正式证书记录。重复请求、任务重试、输出格式增加均不另发新编号。

签发版本引用历史模板和印章版本，不能使用“当前最新模板”临时替代。文件保存摘要、大小、类型和生成版本，便于内部一致性检查及后续文件验签扩展。

## 会签与权限

审批事务需要锁定批次，核对提交版本、所需部门、审批人授权和本部门公章版本，再写入决定。最后一项批准提交时，在同一事务内登记唯一签发任务，防止漏发与重复入队。

修改名单时生成新版本并使旧审批不能用于签发。旧页面的审批请求携带旧版本时返回冲突，不能自动套用到新数据。多人编辑使用版本检查，避免覆盖彼此修改。

批次审批和作废审批是两条状态流。作废申请处于审核中时，证书有效状态保持有效；所有部门批准后才更新为作废。

超管应急使用独立操作类型，保存原因、再次验证结果、目标版本和影响范围，不伪造各部门的批准记录。

接口默认要求认证；公开查询、验证码和登录接口按最小范围开放。列表过滤、对象读取、创建、修改和文件下载均单独落实部门与竞赛数据权限。仅隐藏前端按钮无法控制数据访问。

DRF 的对象级权限不会自动过滤列表中的每条数据，创建也需要单独检查，因此应结合查询集、序列化校验和业务服务实现授权。[DRF 权限说明](https://www.django-rest-framework.org/api-guide/permissions/)

## 后台任务可靠性

任务先持久化，再由 worker 认领，Web 请求不等待整批文件生成。单张任务或小组任务逐步推进批次进度，初期并发采用保守配置，部署后按 CPU、内存和实测调整。

任务领取可以使用 PostgreSQL 行锁和 SKIP LOCKED。官方说明该机制可用于多个消费者访问队列表，但其本身不提供完整任务系统，需要补齐下列机制。[PostgreSQL 锁与队列说明](https://www.postgresql.org/docs/current/sql-select.html#SQL-FOR-UPDATE-SHARE)

- 唯一任务键、租约、心跳和超时重领。
- 领取代次检查，阻止超时旧进程回来覆盖新结果。
- 临时文件按尝试隔离，检查完成后再登记正式文件。
- 重试采用原证书记录和原编号，明确可重试与不可重试错误。
- 进程重启后从持久化状态继续，已有正确文件可以复用。
- 全批就绪后统一发布；未完成任务不作为已签发证书提供给公开查询。
- 审批、任务创建、正式发布分别设置数据库一致性约束。

本方案选择数据库任务表以减少首期部署组件。需要通过并发认领、进程中止和恢复测试验证，不能仅依赖进程内队列或定时轮询保证正确性。

## 排版与签名

模板采用受约束的字段结构，记录页面尺寸、图层、字体、文本区域、背景、印章位置和编号显示设置。禁止将任意脚本或任意 HTML 作为模板执行。

编辑预览与服务端输出共享坐标、字体资源和布局规则。正式提交前生成服务端样张，批量检查文字溢出、缺字及印章越界。画布组件、渲染方式和字体嵌入需通过样张验证后锁定。

长名单自动换行并在字号上下限内适配，仍无法容纳时返回具体记录和字段，不静默裁切。部署字体在本地提供，正式运行不依赖在线字体或外部图片链接。

正式 PDF 在完整背景、文本和公章布局完成后，按批准部门依次追加数字签名。后续签名不能使前序签名失效，最后签署后冻结归档文件。pyHanko 支持 PDF 签名，多个签名使用增量更新，需验证各签名覆盖范围及修改策略。[pyHanko 签名说明](https://docs.pyhanko.eu/en/stable/cli-guide/signing.html)

签发前复核印章和签名证书的启用状态及有效期。选定资源已停用或无法使用时，暂停任务并提示相关部门，不擅自替换为另一枚印章或另一份证书；需要改变签发内容时重新走版本和审批流程。

首期应在真实生成文件上执行内部签名与归档摘要检查，再生成或确认对应图片。用户上传文件验签属于后期，内部签发质量检查仍属于首期。

部门私钥加密保存，解密密钥与数据库分开配置，限制 worker 访问；不将私钥返回前端。密钥轮换保留历史公钥及记录，历史文件不重新签名覆盖。

自签 PDF 的信任配置、图片与 PDF 的区别见需求说明。每份证书是否已业务作废，以平台记录为准，不能仅凭 PDF 的数学签名状态判断。

## 登录与访问保护

同源部署优先复用 Django 服务端会话，使用受保护的 Cookie 和 CSRF 防护。Pure Admin 登录状态与实际权限对接后端，不沿用演示账号、模拟接口或前端固定角色作为正式授权。

Django 提供 CSRF 保护，前端请求需按其机制携带令牌；登录和敏感写操作不能因为使用 API 而关闭保护。[Django CSRF 说明](https://docs.djangoproject.com/en/5.2/howto/csrf/)

增加登录失败限制、敏感操作再次验证、密码重置和权限变更留痕。正式校园网入口使用 HTTPS，访问证书由学校现有条件或内部信任配置解决，不以购买外部证书为前提。

编号查询每次校验服务端验证码，设置查询频率限制，限制连续枚举。管理员免验证码使用独立鉴权路径，返回信息仍受权限控制。公开字段白名单与姓名脱敏在服务端统一应用。

背景、公章、Excel 等上传检查类型、体积和解析资源；避免压缩包膨胀、公式执行和路径穿越。受控渲染进程限制外部网络和任意文件读取，不让模板资源触发不受控请求。

## 存储与本机备份

业务数据库、正式文件、模板、字体和密钥材料使用持久化位置，容器重建不清空这些内容。原始公章和正式证书不使用可猜测的公开静态路径下载。

本机备份生成清单、摘要及完成标记；密钥相关材料单独加密，恢复所需解密凭据不能和密文未经保护地一起保存。数据库与文件清单需保持一致，避免恢复后只有记录没有文件。

定期维护只清理过期临时文件、普通运行日志和按策略轮换的备份，不删除正式证书及关键业务记录。备份失败和磁盘不足产生站内提醒及维护日志。

上线前在隔离的测试数据库和目录中演练恢复，并抽查证书、审批记录和签名资料。由于目前只有同机存储，恢复演练不能证明具有整机或存储损坏后的恢复能力。

## 体验改进版实际实现

负责人角色存入 competition_owners 全局用户组；部门成员关系只用于管理员权限。迁移保留既有负责人关联作为回滚兼容数据，权限判断不再依赖这些旧关联。部门管理员与超管均可正常审批本人提交或修改的批次，普通负责人仍无审批权限。竞赛废止只冻结新业务，不删除旧证书。

模板选用页复用 Pure Admin 官方 CardList 商品卡片页，来源固定到 fae75ad1cd52d11a7279931ef5bba2b80e363c7b；源码副本、MIT 许可与改动说明位于 docs/upstream/pure-admin-card-list。

本地字体与源包摘要记录在 backend/font-assets/manifest.json。镜像构建时准备并校验，启动时缓存到媒体卷以纳入备份，运行时不访问字体 CDN。正文布局通过同一个 layout_text 函数生成浏览器 SVG 与 PDF 的字形运行段、字号、换行和基线。缺字先回退内置中文字体，仍缺失则在提交前返回具体行与字符。

字体文件上传上限 40 MiB，Nginx 请求上限 48 MiB，普通 JSON 请求内存上限 12 MiB；大上传沿用 Django 临时文件处理。文字排版请求排除背景图数据，避免每次拖放或改字体重复上传大背景。

字体文件按 SHA256 固定内容，超管只修改显示名和启用状态，不覆盖既有文件。渲染前由主进程解析全部字体路径、关闭数据库连接，再提交给进程池；渲染子进程不访问字体 ORM。已有模板引用的停用字体仍可读取以维持历史布局。

字体库向所有已登录用户开放导入和预览，重命名与启停仅超管可用。页面复用现有 Pure Admin / Element Plus 数据表、弹窗和详情抽屉。业务区域统一使用主题颜色变量；表格列保留最小可读宽度并在表内滚动；商城卡片固定标签、标题和操作区布局，防止部门名换行改变卡片高度。

文字样式采用布尔字段 bold/italic/underline，布局为描边、切变及下划线预留边距；浏览器 SVG 和 PDF 使用相同几何，不依赖额外商业字重。图形为受约束 rect/ellipse/line/freehand 图层，线点归一化到0..1以便缩放；每条最多1000点，总计5000点，几何完整性和颜色均校验。数组顺序表示图层层级。

校徽原 PNG 保留，SVG 以68×68视口裁出左侧校徽并加白底。useNav.getLogo、登录及favicon统一引用school-emblem.svg，未重新绘制校徽。
