## 技术约束

- 前端使用 vue-pure-admin，基于官方 pure-admin-thin，按需复用完整版的用户、部门、权限、日志、上传、表格及 PDF 预览组件。沿用模板的布局、主题、表单、表格、弹窗和交互风格，不另起一套管理界面设计。
- 官方仓库为 [vue-pure-admin](https://github.com/pure-admin/vue-pure-admin) 和 [pure-admin-thin](https://github.com/pure-admin/pure-admin-thin)。记录实际使用的上游版本或提交，保留版权及许可信息。
- 证书编辑器是专门的业务区域，可以集成免费开源画布能力；周边工具栏、属性面板、列表和弹窗继续使用模板组件。必须能可视化操作并保存，不能以一组静态截图或纯文本 JSON 输入框替代。
- 后端使用 Django 5.2 LTS、Django REST Framework、PostgreSQL。Excel 使用 openpyxl；PDF 自签使用 pyHanko 及所需加密库。选择兼容且仍受支持的运行版本并锁定依赖。
- 按现有技术方案使用数据库持久化任务和独立 worker，补齐租约、超时恢复、幂等及并发保护。不要用进程内后台列表代替可靠任务系统。
- 使用 Docker Engine 与 Docker Compose 部署，主要服务为 web、api、worker、db；api 和 worker 可复用应用镜像。
- 运行期间所需中文字体、图标、背景和脚本随部署提供；不依赖外部 CDN、在线 Mock、付费验证码、短信、商业数字证书或其他付费服务。
- 前端演示账号及权限、Mock API 不能作为正式登录与授权。所有实际业务通过后端和数据库运行。

## 不得改动的业务规则

1. 首期仅团队证书，每队一张。成员只要求姓名，不要求学号、学院或学生名册接口。证书展示哪些字段由管理员在模板中配置。
2. 部门管理员和负责人均可创建竞赛，创建提交即生效。需要审批的是获奖名单和签发申请，不是创建竞赛本身。
3. 同一负责人可以关联多个部门，一项竞赛可以有多位负责人。各部门授权和具体竞赛数据范围必须在后端落实。
4. 使用统一 Excel；奖项允许自由填写，创建竞赛时可以预设供选用，但不能因填写了预设之外的奖项而拒绝导入。初始字段和填写说明参考需求说明。
5. 整批名单提交给全部拟盖章部门并行会签；每个部门任意一位有权限且符合回避要求的管理员批准即可。普通流程必须全部部门通过才能签发。
6. 同时提供整批退回和管理员直接修改。修改产生新版本，原有批准失效，全部部门重新审批。提交或直接修改过本批名单的人回避日常审批。
7. 对数据、模板、公章、输出设置和审批部门保留提交快照。不能批准旧页面后签发另一版本，不能用最新模板或新公章覆盖历史。
8. 全部部门批准后自动进入生成任务，不增加管理员再次确认签发。编号全校唯一、系统自动生成、不复用；重试、重复请求和并发执行不能重复发证。
9. 模板库全校共享，发布部门维护原模板，其他部门复制后修改；每个批次一套模板。支持多个背景、文字字段选择、字体排版、公章位置，以及正文编号和编号水印的独立开关。
10. 长名单和长作品名自动换行并在设定范围内缩小字号；仍放不下或缺字时，指出记录和字段并阻止提交，不裁切或静默省略。
11. 各部门自行管理多枚公章、启停和版本，上传启用不需要超管审核。只使用本批获批的印章；签发前发现已停用等问题时暂停处理，不擅自换章。
12. 支持 PDF、图片及 PDF 加图片。PDF 必须有真正的自签数字签名，多部门追加签名不能破坏前序签名，不能只贴一张公章图。即使只发图片，仍保存签名 PDF 原件。
13. 相关管理员和负责人可下载授权范围内单张证书及整批压缩包。原始公章、私钥、原始名单和内部日志不能通过无鉴权地址泄露。
14. 首期查验只用证书编号查询平台记录。访客每次需要服务端验证码，管理员可免验证码一键核验；仍执行服务端权限、限流、公开字段白名单及姓名脱敏设置。
15. 作废需要全部原盖章部门批准。在审批期间或申请被驳回时，原证书继续有效、可查验及下载；全部批准后才作废，保留原编号、文件和历史。
16. 超管有独立应急签发及作废入口，必须填写原因、再次验证密码、完整留痕并发送站内通知；不能用伪造普通部门批准记录实现。
17. 独立账号密码登录，限制连续失败，敏感操作再次验证密码。业务通知仅站内消息、待办及未读提醒。
18. 正式证书、获奖及关键审批、用印、作废记录长期保留。首期做本机定时备份、失败提醒和隔离恢复演练，明确其不具备整机或存储整体损坏后的恢复保障。
19. 单批设计规模为 5000 支团队，对应 5000 张证书，不是 5000 个文件。PDF 和图片输出不另分配证书编号。

以下继续留在后期：个人证书及团队个人同时生成、学生凭编号领取下载、独立防伪码及其水印、二维码防伪、用户上传 PDF 验签、图片原件比对、商业签章平台。编号水印、PDF 自签和内部签发质量检查继续属于首期。

先做只读盘点，记录 CPU 架构、CPU、内存、空闲磁盘、Docker 与 Compose 版本、现有容器、网络、卷和端口占用。随后持续开发、构建和部署，不等待用户再次批准普通步骤。

部署使用独立 Compose 项目名 awardcollection-v1-test 和独立目录，例如 /opt/awardcollection-v1-test 。若路径已被其他项目使用，另选独立路径，不能覆盖。

应用端口优先考虑未占用的 18080；实际根据盘点选择空闲端口并在报告中记录。只添加本项目必要的入口或端口规则，不覆盖 8888 管理入口，不抢占其他站点的 80、443，不直接对外暴露数据库。

保留既有容器、卷、网络和站点。不得全局清理 Docker、删除未知目录、清空业务数据库、重装或重启整个 Docker 服务来完成本项目部署。项目自身的受控重启、镜像更新和隔离故障测试可以执行，不能影响其他应用。

应用、数据库、正式文件、字体与密钥使用持久化位置。准备环境变量示例、实际配置的受限保存方式、健康检查、数据库迁移、超管初始化、重启策略及本机备份。

尽早验证到面板的网络连通和可用部署通道，发现部署障碍时同步继续本地开发。通过面板现有容器编排、终端或可用的受控通道执行；需要时准备镜像及字体的离线导入方案，不因不能 SSH 就直接停止。
