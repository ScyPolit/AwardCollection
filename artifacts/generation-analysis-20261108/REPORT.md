## 单张耗时分解

隔离容器使用同一生产镜像、相同模板，限制1个CPU和2 GiB内存；生产媒体只读，使用测试姓名、320像素测试印章及临时签名密钥。排除首次启动后，两个基线样本平均2.93秒：

| 阶段 | 平均耗时 | 占单张总时间 |
| --- | ---: | ---: |
| PDF排版及浏览器输出 | 0.88秒 | 30.1% |
| 一枚部门数字签名 | 0.76秒 | 26.1% |
| PDF转PNG及PNG编码写入 | 1.27秒 | 43.3% |

图片阶段中，PDF栅格化约0.64秒，PNG编码写入约0.62秒；签名阶段中，重新加载PKCS#12约0.234秒。这些是包含关系，不能将子项再与父项相加。测试输出位于临时文件系统，没有覆盖正式磁盘写入和数据库提交的完整耗时。

同一隔离进程的首次启动共44.38秒，其中模板/字体准备约37.73秒；正式单张批次的25.66秒也显示了明显启动成本，但不同环境下不能将两者直接等同。

在隔离进程中试验缓存签名器后，两个完全命中缓存的样本平均2.78秒，证书加载时间接近零。样本量很小、其他阶段也有波动，因此只证明重复加载可避免，不承诺整体固定提速比例。

首次隔离尝试在较低资源限制下出现Chromium页面崩溃；有效测量使用2 GiB及512个PID上限。该隔离失败不代表生产任务失败。全部基准数据使用合成内容，未使用正式签名私钥。证据：[原始阶段计时](isolated-profile.json)、[统计摘要](profile-summary.json)。

## 原因与代码位置

1. **逐张串行是已确认的吞吐量瓶颈。** `runworker.py:22`默认并发1，`:86`按该值创建进程池，在途任务也不超过并发数。PPT模板还有最多2个进程的代码上限，因此仅设置环境变量为4不能得到4并发。当前批次排队几乎为零，等待主要发生在逐张处理阶段。
2. **每批重新创建渲染进程池，存在冷启动。** 同一批内部已经复用Chromium和已加载页面；不能误诊为“每张证书都重新启动浏览器”。不过每批退出池时会释放浏览器，小批次尤其受启动、字体加载影响。
3. **图片处理和大素材带来可测量的成本。** 模板JSON约2.34 MB，底图JPEG为2953×2079、约1.75 MB；正式印章在PDF中为1200×1200图像。采样中每张PDF平均2.82 MB、PNG平均3.86 MB。A4当前输出PNG为1684×1190，图片转换编码在合成样本中占时最多。
4. **存在可消除的重复工作。** `renderer.py:255`每个部门、每张证书重新加载PKCS#12；`presentation.py:236`反复序列化模板来识别字体，`ppt_renderer.py:84`每张重新构造并散列准备参数。热态模板准备本身约0.077秒，属于次级优化点。
5. **预览、生成和ZIP共用一个工作循环。** `runworker.py:163`先处理文件任务，随后完整处理一个生成批次，中途不会返回检查预览队列。大批次可能让新预览等待；大量文件任务也可能让后续生成排队。本次采样没有待处理预览，且生成排队0.020秒，因此该结构不是本批次17分钟的直接排队原因。

源码：[工作进程](../../backend/awards/management/commands/runworker.py)、[渲染与签名](../../backend/awards/renderer.py)、[浏览器复用](../../backend/awards/ppt_renderer.py)、[字体扫描](../../backend/awards/presentation.py)、[文件准备](../../backend/awards/prepared.py)。

## 内存与下载的边界

worker限额2 GiB。采样后 `memory.peak` 恰为2 GiB，`memory.events.max` 为12161，OOM及OOM kill均为0；内存直接回收扫描约142万页。批次完成后占用主要是文件缓存，匿名内存约131 MiB。`memory.pressure`累积停顿约11.95秒，是该容器生命周期总量，不能全部归给本次批次，也不足以解释17分钟的全部耗时。

Linux文档将`memory.events.max`定义为即将超过内存上限的次数；回收失败才可能进入OOM，不能把该计数当作OOM次数。见[Linux 6.8 cgroup v2说明](https://www.kernel.org/doc/html/v6.8/admin-guide/cgroup-v2.html)。原始数据见[内存与回收](memory-pressure.json)。

百兆网口限制影响客户端传输约2 GB的下载包，不直接限制服务器内部逐张生成。用户可感知的总等待应拆成：证书生成、ZIP准备、网络下载。旧验收中512 MiB隔离环境打包约163秒属于历史数据，不冒充本次生产ZIP准备耗时；本次只核验ZIP已就绪，未新增打包阶段精确计时。

## 建议的优化顺序

1. 在这台主机建立独立部署参数，先验证2个渲染进程、worker 4 GiB上限；低配置部署仍保留单进程配置。需用同等300张批次比较耗时、峰值内存及签名完整性，不能承诺线性翻倍。
2. 将生成与预览/文件准备划为独立队列和资源预算，避免预览被整批生成阻塞。补齐每阶段耗时、速度及预计完成时间，分别展示生成和ZIP进度。
3. 复用跨批次的有界渲染进程，并按模板、公章、字体版本失效；在受限进程内缓存签名器，密钥轮换或文件变化时失效。
4. 在新模板版本中优化底图、印章的合理分辨率，评估保持像素一致的更快PNG编码。低压缩级别可能增大下载包，必须同时比较CPU、体积与视觉效果。素材优化应在签名前进行，历史签名PDF保持原件。

最优先的收益来自合理并行和图片处理；仅缓存签名器或微调数据库，无法消除当前主要耗时。有效验收需同时检查中文无缺字、排版、公章、PDF签名、PNG视觉一致性、批量幂等和低内存稳定性。
